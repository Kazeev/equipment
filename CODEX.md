# Индексация DOCX · Camunda 7

MVP: Java 17, Spring Boot 3.5.6, Camunda 7.24, React, H2. Один файл — одна заявка и один экземпляр процесса.

## Запуск

Требуются JDK 17+, Node.js 20+. Maven можно установить отдельно или использовать `run-backend.ps1`, который скачивает Maven в `.tools` при необходимости. При первом запуске нужен интернет для зависимостей.

Из корня проекта:

```powershell
.\run-backend.ps1
```

Во втором терминале:

```powershell
cd frontend
npm install
npm run dev
```

Открыть http://localhost:5173. Backend: http://localhost:8080. Интерфейс обновляет список каждые 5 секунд.

## Проверка руками

1. Создать Word-документ с первой таблицей из двух столбцов. Первая строка — заголовки `uid`, `name`, следующие — оборудование.
2. Скопировать DOCX в `src/main/resources/input`. Пример строки: `SN-001 | Ноутбук`.
3. После двух проверок папки (примерно 3–6 секунд) задача появляется в React без исполнителя.
4. Открыть задачу: она назначится пользователю `demo`, появятся ID заявки, файл и оборудование.
5. Закрытие формы сохраняет назначение. «Просмотрено / Завершить» завершает задачу и процесс.
6. Повторно положить файл с тем же именем: новая заявка не создаётся.

Сгенерировать пример без Word: `mvn -Dtest=SampleDocumentTest test` (создаст `src/main/resources/input/equipment.docx`), затем скопировать его во входную папку.

## Данные и обработка

- `requests(id, file_name)` — индексированные файлы / заявки. Имя уникально, сравнение с учётом регистра.
- `equipment(id, request_id, uid, name)` — строки оборудования; внешняя ссылка на заявку.
- Camunda создаёт свои служебные таблицы в той же H2. База хранится в `data/` и переживает перезапуск.
- BPMN: `src/main/resources/processes/document-review.bpmn`, можно открыть в Camunda Modeler.
- Обнаружение файлов — Spring scheduler. Файл обрабатывается после двух совпавших проверок размера и времени изменения. Для больших файлов рекомендуется копирование под временным расширением и переименование в `.docx` после завершения копирования.
- Чтение, запись бизнес-данных и создание пользовательской задачи выполняются синхронно в транзакции запуска Camunda. При ошибке транзакция откатывается, файл попадает в `input/error` вместе с описанием; исправленный документ можно вернуть во входную папку.
- Успешные и повторные документы переносятся в `input/archive`. Ошибка переноса не приводит к повторной индексации благодаря уникальному имени в БД.
- Используется первая таблица документа; первая строка считается заголовками. Пустые строки пропускаются; оба значения обязательны. Повторяющиеся UID допустимы.
- Для собранного JAR входная папка должна быть обычной внешней папкой: `$env:INPUT_DIRECTORY='C:\documents\input'`. Ресурсы внутри JAR нельзя использовать как входную папку. По умолчанию путь относительно рабочей директории.
- MVP рассчитан на один экземпляр приложения. Константный `demo` без аутентификации предназначен для локальной демонстрации.

## Просмотр истории через H2

После запуска backend открыть http://localhost:8080/h2-console. Подключение выполняется внутри приложения и не конфликтует с блокировкой файла:

- Driver Class: `org.h2.Driver`
- JDBC URL: `jdbc:h2:file:./data/workflow;DB_CLOSE_ON_EXIT=FALSE`
- User Name: `sa`
- Password: пустой

```sql
SELECT r.id AS request_id, r.file_name,
       t.name_ AS task_name, t.assignee_, t.end_time_
FROM act_hi_taskinst t
JOIN act_hi_procinst p ON p.proc_inst_id_ = t.proc_inst_id_
JOIN requests r ON r.id = p.business_key_
WHERE t.end_time_ IS NOT NULL
ORDER BY t.end_time_ DESC;
```

Подключение из отдельной IDE к тому же файлу при работающем backend вызывает ошибку 90020. Для такого подключения нужно остановить backend; веб-консоль позволяет оставить его работающим.

## REST API

В React вкладка «Закрытые мной» показывает завершённые пользователем `demo` заявки, дату завершения и карточку оборудования без редактирования. Источник — история Camunda; отменённые задачи исключены. Доступность истории ограничена её сроком хранения (BPMN: 30 дней).

- `GET /api/tasks/completed` — завершённые заявки текущего пользователя.
- `GET /api/tasks/completed/{id}` — карточка завершённой заявки с оборудованием.

- `GET /api/tasks` — все активные задачи Camunda без исполнителя или назначенные на `demo`.
- `POST /api/tasks/{id}/open` — назначение через claim и получение карточки. Чужая задача возвращает 409.
- `POST /api/tasks/{id}/complete` — завершение своей задачи, ответ 204.

## Автоматические проверки

```powershell
.\run-backend.ps1 -Test
cd frontend
npm run build
```

`WorkflowTest` проверяет реальный DOCX, запись оборудования, незанятую задачу, claim, повторный импорт и завершение процесса. `SampleDocumentTest` создаёт пример документа.

`DocxParserTest` проверяет пустые и повреждённые документы, число столбцов, обязательные значения, ограничения длины, пробелы, пустые строки и повторяющиеся UID.

`SystemTest` запускает настоящие Camunda и H2 с HTTP API через MockMvc: стабильность входного файла, архивирование, пропуск дублей после перезапуска обработчика, игнорирование временных файлов, исправление и повторную загрузку ошибочного документа, откат при ошибке БД (в том числе после частичной вставки оборудования), фильтрацию задач по исполнителю, повторное открытие, завершение и фильтрацию истории. Используются отдельные тестовые базы в памяти и временные папки; рабочая база `data/workflow` не затрагивается. Браузерные проверки React в этот набор не входят.
